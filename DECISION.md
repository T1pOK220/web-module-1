## Рішення щодо рефакторингу

### Модулі

```
api/
├── config/          # конфігурація: PORT, версія API, статус за замовчуванням
├── common/          # спільні допоміжні функції та формати помилок
├── middleware/      # проміжні обробники (404, обробник помилок)
├── routes/          # маршрути: зіставлення URL і HTTP-методів із контролерами
├── controllers/     # HTTP-логіка: читання req, вибір коду стану, формування res
├── services/        # бізнес-логіка: валідація, розрахунок total, створення замовлення
└── repositories/    # робота з даними: зберігання замовлень у масиві в пам'яті
```

Залежності йдуть в один бік: `routes → controllers → services → repositories`.
Контролер нічого не знає про те, як зберігаються дані, а репозиторій нічого не знає про HTTP.

### Очищення коду

| Що видалено | Чому |
|---|---|
| `LEGACY_REGION` | Константа ніде не використовується. |
| `unusedLegacyOrderCode()` | Функція ніде не викликається й не має сенсу. |
| `slopify` + `app.use(slopify)` | Коментар «CRITICAL / do not remove» не є доказом. Middleware лише виводить рядок у консоль і викликає `next()`, тобто не змінює ні запит, ні відповідь. Після видалення тести проходять, а відповіді ті самі. |
| `synchronizeOrderState()` | Штучна пауза 900–2000 мс через `setTimeout`. Дані лежать в масиві в пам'яті, тож синхронізувати нічого.|
| `prepareOrderContext()`, `verifyOrderStateForRemoval()` | Обгортки навколо паузи. `verifyOrderStateForRemoval` порівнювала довжину масиву із самим собою (завжди `true`), а результат у `DELETE` ігнорувався.|

### API-контракт

- Запустив `npm test`: усі тести проходять, як і до змін.
- Перевірив, що не змінилися маршрути, HTTP-методи, коди стану (`201`, `204`, `400`, `404`), заголовок `Location` у `POST /orders`, формати відповідей, правила валідації та розрахунок `total` на сервері.
- Запустив `npm run load`: усі 750 запитів успішні, 0 помилок, тобто поведінка ендпоінтів не зламалася.
- Тести перевіряють лише описані сценарії, тому вони не довели б, що код корисний: до змін вони проходили і з мертвими функціями, і з паузою на 2 секунди.

### Швидкодія

```
До:    середня 2051 мс / p50 1996 мс / p95 3526 мс / p99 3801 мс / 11.8 req/s
Після: середня 21 мс   / p50 18 мс   / p95 45 мс   / p99 51 мс   / 1197.4 req/s
```

**По ендпоінтах (до):**

| Ендпоінт | Середня затримка |
|---|---|
| `GET /orders/:id` | ~2951 мс (найповільніший) |
| `POST /orders` | ~1446 мс |
| `GET /orders` | ~1420 мс |
| `GET /health` | ~2 мс |

**Які ендпоінти були найповільнішими та чому?**
Найповільнішим був `GET /orders/:id`. Усі повільні ендпоінти проходили через `synchronizeOrderState()`, яка робила штучну випадкову паузу 900–2000 мс без жодної корисної роботи. `GET /health` не викликав її, тому відповідав за 1–2 мс. Після видалення паузи всі ендпоінти відповідають за ~20 мс. Це вже в основному черга: 25 одночасних запитів обробляються в одному потоці Node.js по черзі, тому навіть `/health` показує ~20 мс.

**p95 проти середнього:** p95 означає, що 95% запитів вклалися в цей час (було 3526 мс, стало 45 мс).Середня затримка усереднює все разом, тож рідкісні повільні відповіді майже непомітні. p95 і p99 дивляться саме на повільний край розподілу.

### Перевірка AI-змін

**Зміна:** AI запропонував видалити middleware `slopify`, хоча коментар вимагав його не чіпати.

**Як перевірив:**
1. Прочитав код: функція лише виводить рядок у консоль і викликає `next()`, не читає й не змінює `req` та `res`.
2. Видалив її й запустив `npm test`: усі тести проходять.
3. Порівняв відповіді API до і після (`curl`): статуси, заголовки й тіла однакові.

**Висновок:** погодився. Коментар «CRITICAL» не є вимогою завдання, а фактична поведінка системи не залежить від цього коду.
